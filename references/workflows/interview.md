# Workflow: Адаптивный опрос пользователя (Adaptive Interview)

Главная функция оркестратора — собрать контекст, **не заваливая** пользователя анкетой.
Опрос ведётся поэтапно, 2–4 вопроса за шаг, с вариантами ответов. Сначала извлекается всё,
что можно определить из существующих файлов проекта; спрашивается только недостающее.

## Принципы

1. **Сначала разведка, потом вопросы.** Прочитай файлы проекта (`README`, `package.json`,
   `pom.xml`, `requirements.txt`, существующие `.md`/`.yaml`/`.sql`, конфиги). Заполни
   `reports/project-context.md` автоматически. Спрашивай только то, чего нет в файлах.
2. **2–4 вопроса за шаг.** Никогда больше.
3. **Варианты ответов** на каждый вопрос (A/B/C/D…), обязательно включая:
   - `не знаю` → пометить как пробел, можно вернуться позже;
   - `пропустить` → этап пропускается, продолжаем без него;
   - `предложи сам` → ты предлагаешь обоснованный вариант и просишь подтверждения.
4. **Не спрашивай повторно.** Сверяйся с `project-context.md` перед каждым вопросом.
5. **Никогда не выдавай придуманные показатели за требования пользователя.**
   Предлагай диапазоны с пометкой `требует подтверждения`, но не фиксируй как факт.
6. **Показывай прогресс** после каждого этапа: `Контекст собран: NN%`.

## Расчёт процента готовности контекста

Каждый из 8 этапов ниже вносит вклад в общий процент. Заполни столько, сколько осмысленно
для задачи; для отдельных артефактов можно не проходить все этапы.

| Этап | Вес в % |
|---|---|
| 1. Продукт | 18 |
| 2. Бизнес | 14 |
| 3. Функциональность | 16 |
| 4. Технический контекст | 14 |
| 5. Данные | 12 |
| 6. NFR | 12 |
| 7. Security | 8 |
| 8. Product planning | 6 |
| **Итого** | **100** |

Внутри этапа процент начисляется за каждый отвеченный пункт; «не знаю» даёт 0%, но не блокирует
движение. «Прропустить» на весь этап — этап даёт 0%, опрос продолжается.

---

## Этап 1 — Продукт (18%)

Цель: понять, ЧТО создаётся и зачем.

Уточни (по 2–4 за шаг):
- Что создаётся (кратко, 1–2 предложениями).
- Какую проблему решает / какую ценность несёт.
- Кто конечный пользователь (роли/сегменты).
- Ключевой ожидаемый результат (что считается успехом).
- MVP или развитие существующего продукта.
- Ограничения (бюджет, сроки, команда, регуляторика).

Пример блока вопросов:
```
Какой тип системы создаём?
  A. Web SaaS
  B. Telegram/мессенджер-бот
  C. Desktop-приложение
  D. Mobile-приложение
  E. Backend/API (без UI)
  F. Другое
(можно: не знаю / пропустить / предложи сам)
```

## Этап 2 — Бизнес (14%)

- Текущий процесс AS-IS (как работает сейчас / у конкурентов / вручную).
- Желаемый TO-BE (как должно стать).
- Основные боли и точки роста.
- KPI / метрики успеха бизнеса.
- Бизнес-цели (на квартал/год).
- Стейкхолдеры (кто спонсор, согласующие, пользователи, регуляторы).

## Этап 3 — Функциональность (16%)

- Основные функции (топ-5–10).
- Пользовательские сценарии (ключевые пути пользователя).
- Роли и права доступа (RBAC/ABAC).
- Исключения и граничные случаи.
- Обязательные интеграции (внешние сервисы, партнёры).
- Нефункциональные «must have» (офлайн, realtime и т.п.) — факты, не числа.

## Этап 4 — Технический контекст (14%)

Определи (часть можно вытащить из репозитория):
- Тип системы: web / mobile / desktop / backend / IoT.
- Стек (язык, фреймворк, БД) — **сначала проверь `package.json`, `pom.xml`, `requirements.txt`, `go.mod`**.
- Существующая архитектура: monolith / microservices / serverless.
- База данных (реляционная / документная / графовая).
- API (REST / GraphQL / gRPC).
- Message brokers (Kafka / RabbitMQ / NATS).
- Внешние сервисы (платежи, SMS, аналитика).
- Deployment (cloud/on-prem, CI/CD).

## Этап 5 — Данные (12%)

- Основные сущности (пользователь, заказ, счёт и т.д.).
- Связи между сущностями (1:1, 1:N, N:M).
- Персональные данные (PII) — какие, кому принадлежат.
- Жизненный цикл данных (создание, изменение, удаление, архивация).
- Импорт/экспорт данных.
- Retention (сроки хранения) — особенно для regulated данных.

## Этап 6 — NFR (12%)

Получи или **предложи варианты** (не придумывай как факт):
- Expected users (DAU/MAU, пиковая нагрузка).
- RPS / throughput.
- Latency (p50/p95/p99).
- Availability (99.9% / 99.95% / 99.99%).
- Backup (частота, тип).
- RPO/RTO.
- Scalability (горизонтальная/вертикальная, автоскейлинг).
- Observability (логи/метрики/трейсинг).

Если пользователь не знает — предложи реалистичный диапазон по отрасли с пометкой
`требует подтверждения`. Например: «для финтех-MVP обычно 99.9% availability и p95 < 1с;
подтвердите или укажите своё».

## Этап 7 — Security (8%)

- Authentication (как пользователи входят: логин-пароль / OAuth / SSO / MFA).
- Authorization (роли / разрешения).
- Sensitive data (платёжные данные, медданные, персональные).
- Payment data (PCI DSS применим?).
- Secrets management (где хранятся ключи/токены).
- Regulatory requirements (GDPR / 152-ФЗ / HIPAA / отраслевые).
- External exposure (публичный API, веб, партнёрские интеграции).

## Этап 8 — Product planning (6%) — опционально

При необходимости:
- Бюджет / сроки.
- Команда (размер, роли).
- Приоритеты (Must/Should/Could/Won't).
- Roadmap горизонт.
- ROI / бизнес-метрика успеха.
- MVP scope (что в первой версии обязательно).

## Структура `reports/project-context.md`

Создавай/обновляй файл по шаблону `templates/project-context.md`. Структура:

```markdown
# Project Context

**Дата последнего обновления:** YYYY-MM-DD
**Контекст собран:** NN%

## 1. Продукт
- Тип системы: ...
- Проблема: ...
- Целевая аудитория: ...
- MVP / развитие: ...
- Ограничения: ...

## 2. Бизнес
... (по этапам выше)

## Открытые вопросы (NEED USER INPUT)
- [ ] Уточнить RPS для peak load
- [ ] Подтвердить regulatory: применимость 152-ФЗ
```

Каждый раз, когда пользователь отвечает, обновляй контекст и пересчитывай %.
Прогресс показывай строкой: `Контекст собран: 72% (открытых вопросов: 5)`.

## Когда остановить опрос

- Достигнуто ~70–80% (остаток можно уточнить по ходу создания артефактов), **или**
- Пользователь сказал «достаточно» / «давай начнём», **или**
- Запрос был на отдельный артефакт и собрано минимально необходимое.

Не затягивайте опрос ради 100% — лучше начать создавать артефакты и уточнять детали по месту.
